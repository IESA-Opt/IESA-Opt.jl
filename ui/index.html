IESA-Opt.jl

        
IESA-Opt.jl is a Julia/JuMP implementation of the IESA-Opt integrated energy system model. It supports transition studies with annual investment decisions, hourly or representative time-slice operation, technology stock evolution, energy balances, policy constraints, and solver-backed optimization.

        

          GitHub repository
          Documentation
          Outputs guide
        


        
Using the dashboard

        
The dashboard is organised into sections along the very top — each section is its own workspace with its own set of tabs underneath:

        
    
          
  • Single run — the default workspace. Tabs: Setup, Progress, Results. Used to launch one optimisation, watch it solve, and inspect the resulting output folder.
    • 
          
  • Scenario Space — the campaign workspace for sampling-based uncertainty studies. Tabs: Parameter Space (define the parameter space + sample variants), Progress (live multi-worker campaign progress with pause / resume / stop controls), Results (aggregated cross-variant analytics with a campaigns sidebar), Analysis (Scenario Discovery + global sensitivity analysis).
    • 
          
  • Scenario explorer — workbook and generated-model inspection. Tabs: Input overview, Technology atlas, Cost assumptions, Activity map, Coupled Sectors, Flow details, Profiles 3D, Policy, Model browser, Technology dependencies.
    • 
          
  • MGA — solver-backed modelling-to-generate-alternatives campaigns with near-optimal cost caps and ORACLE refinement. Tabs: Configure, Progress, Results.
    • 
          
  • About — this reference page.
    • 
        

        
The tabs below the section bar are filtered automatically: only the tabs that belong to the active section are shown. Each tab is described below together with every option it exposes.


        
Help and navigation

        
The upper-right toolbar contains the Julia status pill, the UI search box, and a Help switch below search. Help is off by default so the workspace stays uncluttered. Turn it on to show small i icons next to controls, headings, buttons, generated radio buttons, and generated checkboxes.

        
    
          
  • Help switch — toggles contextual help anchors on and off. When it is off, the i icons are hidden and no hover help opens.
    • 
          
  • i icons — hover or focus an icon to open a pointed help dialog. The dialog points to the icon that triggered it.
    • 
          
  • Read more — expands the dialog with extra detail. After expanding, the dialog stays open while the pointer is nearby, closes after the pointer remains outside for about one second, and closes immediately when the user clicks elsewhere.
    • 
          
  • Search the UI — opens the keyboard-search dialog for workspaces, tabs, and About-page references. Use Ctrl K to open it quickly.
    • 
          
  • Workspace tabs — only tabs belonging to the active top-level workspace are shown. For example, Single run shows only Setup, Progress, and Results; Scenario Space shows Parameter Space, Progress, Results, and Analysis.
    • 
        


        
Single run workspace

        
Single run launches and reviews one optimisation at a time. Its three tabs follow the normal run lifecycle: Setup defines the model and solver options, Progress watches the active solve, and Results inspects completed output folders.


        
Setup tab

        
This is the launchpad for a new optimisation. The left summary card starts the run; the main setup area groups Scenario beside Solve Mode, then Solver Settings beside Temporal Resolution. Press Run model to start; the page will switch to Progress automatically.

        
    
          
  • Solver — chooses the optimisation backend (HiGHS, Gurobi, etc.). The detail line shows the solver version detected on the system.
    • 
          
  • Solve method — algorithm hint passed to the solver (for example simplex, barrier, auto). Available options depend on the selected solver. With Help icons on, each method has its own Read more explanation; for example, Barrier is described as an interior-point LP method that often works well on large models and can use parallel CPU threads.
    • 
          
  • CPU threads — threads given to the solver; 0 lets the solver pick.
    • 
          
  • Input workbook — picks one of the Excel workbooks bundled in the Input/ folder.
    • 
          
  • Browse… — selects an Excel/Parquet file from anywhere on disk; Clear reverts to the dropdown selection.
    • 
          
  • Years selection — chooses which model years (periods) to solve. Multiple years may be selected to run a transition path.
    • 
          
  • Time slicing — when on, the model runs on representative days; when off, it runs on full chronological hours.
    • 
          
  • Representative days — number of typical days the clustering algorithm produces (only relevant with time slicing on).
    • 
          
  • Time slices — total operating time slices used by the model, derived from representative days × hours per day.
    • 
          
  • Hours in a day — number of intra-day time slices in a representative day. The 24 hours of the day are aggregated into this many sequential clusters, so chronology within the day is preserved (24 = full hourly resolution, 12 = pairs of consecutive hours, 8 = triplets, 6 = four-hour slices, 4 = six-hour slices, 3 = eight-hour slices, 2 = twelve-hour slices, 1 = single daily slice).
    • 
          
  • Clustering approach — algorithm used to pick representative days (e.g. k-means, hierarchical).
    • 
          
  • Extreme days — how many extreme days (peak demand, low VRES) are forced into the representative-day set on top of the regular clusters.
    • 
          
  • Hourly reports — if checked, hourly profiles are written to the output database (larger files, richer plots).
    • 
          
  • Show violations — relaxes every constraint with an elastic slack at penalty 1e7 per unit (JuMP.relax_with_penalty!) so the solve always returns a feasible point. After the solve the run log lists the constraints whose slack is non‑zero, ranked by magnitude. When this option is off and the model comes back INFEASIBLE, an IIS / conflict analysis is run automatically and the offending constraint names plus a heuristic suggestion are written to the log (works on Gurobi/CPLEX/Xpress; HiGHS support depends on its conflict refinement build).
    • 
          
  • Force extreme periods — ensures the extreme days selected above are guaranteed to appear in the solved problem.
    • 
          
  • Boundary ramping — enforces ramping limits across the boundary between adjacent representative days.
    • 
          
  • MultiRegion — activates the MultiRegion regional-cap extension. When on, it adds grouped regional stock/use caps and applies the MultiRegion stock-bound data convention; when off, the core model is unchanged by this extension.
    • 
          
  • Constraint group — chooses a preset of policy constraints to activate (carbon caps, RES targets, etc.).
    • 
          
  • Output name — Automatic derives a folder name from the timestamp and configuration; Custom lets you type one.
    • 
        


        
Progress tab

        
Live status for the run that is currently solving (or the last one started).

        
    
          
  • Status pill — Idle, Running, Solving, Completed, or Failed.
    • 
          
  • Activity lights — pulse while data reading, model build, and solve stages are active.
    • 
          
  • Stage steps — checklist of pipeline stages with elapsed time per stage.
    • 
          
  • Run log — streamed stdout/stderr from Julia and the solver.
    • 
          
  • Stop run — cancels an in-flight solve.
    • 
          
  • Open results — appears once a run finishes and jumps to its output in the Results tab.
    • 
        


        
Results tab

        
Reads finished output folders and renders charts and tables. The sidebar lists outputs found under Output/.

        
    
          
  • Refresh — rescans the output folders.
    • 
          
  • Compare selected — opens the comparison view for the runs currently ticked in the sidebar (also triggered automatically when two or more runs are selected).
    • 
          
  • Delete selected — permanently removes the selected output folders from disk after a confirmation prompt.
    • 
          
  • Click a run — loads the single-run view (cost, timing, prices, capacities, dispatch, emissions, supply/demand).
    • 
          
  • Ctrl/⌘-click — toggles a run in the compare set.
    • 
          
  • Shift-click — range-selects from the last clicked run.
    • 
        

        
The single-run view shows these panels (each can be expanded to a data table via the Show table button):

        
    
          
  • System Costs — total objective and breakdown by cost component, per period.
    • 
          
  • Solve Time And Solver Stats — wall-clock time per pipeline stage plus solver settings used. Segments: Queue (time spent in the run queue), Data read, Prepare (derived parameters), Cluster (representative-day clustering, skipped in full-hourly mode), Optimizer init (license check + JuMP model construction), Generate (variables, constraints, objective), Solve (solver wall-clock), Extract duals (post-solve CO2 / emission / activity price retrieval), Write (DuckDB output tables).
    • 
          
  • CO2 Price — shadow price of the emission cap, per period.
    • 
          
  • Activity Prices — shadow prices of the energy balance constraints (commodity prices) per region.
    • 
          
  • Power System Capacities — installed generation, storage, and conversion capacities for the power system, per period.
    • 
          
  • Hourly Dispatch — stacked-area dispatch profile over the chosen period and region. Use the period/region/cluster pickers above the chart to change scope; click legend entries to toggle technologies. Trace labels read Tech name (techID), taken from the workbook Technologies sheet.
    • 
          
  • Flexibility Analysis — for one selected flex technology (storage, EV, demand response, gas buffer, etc.), shows the passive reference demand profile, the actual flex profile, the net shift (flex − reference) as translucent bars, and the hourly electricity shadow price on a secondary axis. Below the chart, Show indicators reveals a per-(tech, period) table with ref/flex volumes, shift UP/DW totals, weighted average prices and the cost savings from arbitrage. Sign convention: positive shift means demand increased versus the reference (charging / load-up); negative means demand decreased (discharging / shedding).
    • 
          
  • Emissions — emissions per technology and sector, with optional net line.
    • 
          
  • Supply / Demand — positive flows above zero, negative flows mirrored below, with optional net line.
    • 
        

        
In compare mode the System Costs and Solve Time charts switch to a multi-run stacked view, and the comparison panel shows side-by-side timing and cost-component tables. The single-run-only panels (CO2 Price, Activity Prices, Power Capacities, Hourly Dispatch, Flexibility Analysis, Emissions, Supply/Demand) are hidden because they refer to one run only — click a single row in the sidebar to bring them back.


        
Scenario Space workspace

        
Scenario Space sweeps an entire parameter space rather than a single point. You define which workbook inputs are uncertain (and over what range), pick a sampling method, and the workspace launches one IESA-Opt solve per sampled variant in parallel. The four tabs split the lifecycle: Parameter Space (set up + validate the design), Progress (watch many workers solve), Results (browse the cross-variant outcome space), and Analysis (Scenario Discovery and global sensitivity analysis on the completed runs).


        
Parameter Space tab

        
The setup screen for a campaign. Mirrors Single Run for the model definition (workbook, periods, time-slicing, representative days, extreme periods, reporting flags, advanced settings) but adds the campaign-level controls.

        
    
          
  • Solver and Solve method — same options as Single Run; whichever solver is picked here is used by every variant in the campaign.
    • 
          
  • Total CPU threads + Threads per worker — the global thread budget is split across Parallel workers (one IESA-Opt solve per worker). Threads per worker is computed automatically as floor(threads ÷ workers).
    • 
          
  • Campaign name — folder name under Output/ where every variant's output, the consolidated campaign metadata, and validated parameter space are written.
    • 
          
  • GSA method — selects the global sensitivity analysis pipeline that the Analysis tab will run on the completed campaign: rank (Spearman rank correlations, sampled with Latin hypercube), moment_delta (Borgonovo-style moment-independent delta indices, also LHS), morris (Morris elementary effects with mu / mu* / sigma metrics, requires Morris sampling), or sobol (first-order Sobol variance indices, requires Sobol sampling). The hint line under the dropdown explains the implied sampler.
    • 
          
  • Sampling method — Latin hypercube, Morris, Sobol, or Factorial. Locked to a compatible choice when the GSA method requires a specific sampler.
    • 
          
  • Number of variants + Random seed — controls how many points are drawn (and how many implied IESA-Opt evaluations the chosen GSA will perform — the read-only Implied evaluations field shows the actual count, which exceeds Number of variants for Morris and Sobol).
    • 
          
  • Parallel workers — how many variants are solved concurrently. Each worker gets Threads per worker threads.
    • 
          
  • Parameter Space table — one row per uncertain input, with sheet/row/column references, distribution type, lower/upper bounds (or list values), and an optional override label. Use + Add row / Duplicate / Remove selected to edit, Validate to type-check the bounds against the workbook, and Save / Load parameter space to round-trip CSV definitions.
    • 
          
  • Preview sample — renders the first 20 sampled variants in a table without solving anything — quick sanity check that bounds and distributions are correct.
    • 
          
  • Run campaign — kicks off the campaign and switches to the Progress tab automatically.
    • 
        


        
Progress tab

        
Live status for the campaign that is currently solving (or the last one started). Designed to handle dozens of variants finishing at different rates.

        
    
          
  • Status pill + headline — campaign name, state (queued / running / paused / done / stopped / failed) and the projected finish time given current throughput.
    • 
          
  • Campaign stats — Total / Done / Running / Failed / Queued / Workers counters that update in real time.
    • 
          
  • Progress bar — green portion is variants that completed successfully; the red sliver to the right of it is variants that failed. Footer shows percent done and elapsed time.
    • 
          
  • Pause / Resume / Stop — Pause finishes any variants that are already running but stops launching new ones; Resume picks up where Pause left off; Stop finishes running variants and ends the campaign (cannot be resumed). Start demo animates a fake campaign to preview the layout without solving.
    • 
          
  • Campaign phases — per-phase tiles (sample, baseline, solve, finalize) showing what fraction of each phase is complete.
    • 
          
  • Workers grid — one card per worker with a coloured dot (running / optimal / failed / idle) and the variant currently being solved on that worker.
    • 
          
  • Campaign error — if the campaign task itself raised an exception, the full Julia backtrace is shown here. Hidden when the campaign succeeds.
    • 
          
  • Recent failures — per-variant errors, most-recent first, click to copy. Hidden when no variants failed.
    • 
        


        
Results tab

        
Browses the outcome space of every completed variant in a chosen campaign. The left sidebar lists every Scenario Space campaign captured by the server (newest first); click one to load its variants. The main panel shows the cross-variant outcome scatter:

        
    
          
  • Cost × CO2 price scatter — one marker per completed variant; X-axis is total system cost, Y-axis is the average CO2 price. Hover for the variant ID and the sampled parameter values that produced that point.
    • 
          
  • Refresh — rescans Output/ for new campaigns without reloading the page.
    • 
        


        
Analysis tab

        
Two complementary post-processing tools that run on the campaign selected in Results. Both need completed variants with sampled parameter values, so wait for the campaign to finish before opening this tab.

        
    
          
  • Scenario Discovery — PRIM-style box discovery on the cost / CO2-price outcome of interest. The chart shows the discovered boxes (sub-regions of the parameter space with concentrated outcomes), and the table lists each box's constraints, density, coverage, and the parameters that bound it.
    • 
          
  • Global sensitivity analysis — ranks input parameters by their association with system cost and CO2 price using the GSA method that was chosen in Parameter Space (Spearman rank, moment-independent delta, Morris elementary effects, or first-order Sobol). The chart shows ranked metrics; the table provides the underlying numerical values per parameter.
    • 
        


        
Scenario Explorer workspace

        
The Scenario Explorer is read-only. It does not solve anything — it is a structured way to inspect a workbook (the static inputs) and the JuMP model that IESA-Opt would build from it (the generated structure). Useful when debugging input data, comparing two workbooks, or understanding how the optimisation is wired together. The ten tabs are independent; switch between them freely. Most tabs offer an Input workbook + Period selector to scope the view.


        
Input overview tab

        
The starting point. Pick a workbook and a period, then click Refresh overview to summarise the workbook.

        
    
          
  • Atlas metric cards — high-level counts (sheets, technologies, activities, sectors, time periods, etc.) in the chosen workbook.
    • 
          
  • Workbook shape — bubble chart of every sheet, sized by row count, so you can spot which sheets carry most of the data.
    • 
          
  • Model sets — counts of each loaded model dimension (technologies, activities, sectors, regions, periods, time slices).
    • 
          
  • Sheets — full inventory table with row/column counts per sheet.
    • 
        


        
Technology atlas tab

        
Population view of the technologies in the workbook.

        
    
          
  • Sector / category composition — treemap-style breakdown of technologies by sector and category.
    • 
          
  • Technology economics — scatter of technologies by investment cost vs. variable cost (or efficiency, depending on availability), giving a quick read on the cost frontier.
    • 
          
  • Technology rows — sortable table of the highest-investment-cost technologies with the underlying numbers.
    • 
        


        
Cost assumptions tab

        
Cost-side detail to complement the Technology atlas.

        
    
          
  • Annualized cost stack — bar chart of annualized investment / fixed-O&M / variable / fuel cost per technology or sector.
    • 
          
  • Cost assumptions — full per-technology cost row table.
    • 
        


        
Activity map tab

        
Activities are the energy / material flows the model balances (electricity, hydrogen, methane, freight tonne-km, etc.).

        
    
          
  • Sector / activity balance — heatmap of which sectors produce or consume which activities, magnitude-coloured.
    • 
          
  • Activity demand — bar chart of the largest net demands.
    • 
          
  • Balance rows — the largest sector / activity coefficients with the technologies they come from.
    • 
        


        
Coupled Sectors tab

        
Higher-level system view: which sectors are linked through shared activities. Renders the cross-sector activity graph, with a legend showing the activity classes and a table of the technology paths between sector pairs.


        
Flow details tab

        
Per-technology / per-activity drill-down. Type a search query in the sidebar; the search results list every match. Click one to see:

        
    
          
  • Detail graph — a small directed graph centred on the selected entity, showing every input and every output with edge labels for the coefficients.
    • 
          
  • Detail rows — the same information as a table (Side, Group, Kind, Name, Coefficient).
    • 
        


        
Profiles 3D tab

        
Time-of-use behaviour of the hourly profiles in the workbook (demand profiles, renewables availability, EV charging, etc.).

        
    
          
  • Hourly profile surface — 3D surface of one selected profile across hour-of-day × day-of-year, picked via the dropdown above the chart.
    • 
          
  • Monthly profile fingerprint — heatmap fingerprint of every profile aggregated by month × hour-of-day, useful for spotting seasonal patterns.
    • 
          
  • Profile rows — per-profile summary table with min / max / mean / variability.
    • 
        


        
Policy tab

        
Policy and target inputs that shape the optimisation.

        
    
          
  • Policy constraint catalog — every policy constraint defined in the workbook with its scope and bounds.
    • 
          
  • Policy targets — bar chart of emission and policy targets across periods.
    • 
          
  • Target rows — the same targets in tabular form.
    • 
        


        
Model browser tab

        
Builds an IESA-Opt JuMP model from the chosen workbook (without solving) and shows what is inside.

        
    
          
  • Model shape — Time-slice preview (representative days), Annual, or Full-hourly. Time-slice preview is the fastest way to inspect a representative model.
    • 
          
  • Representative days + Hours per day — the temporal resolution used when the time-slice preview is selected.
    • 
          
  • Generate browser — runs the model build and populates the right-hand stats (rows, columns, build time).
    • 
          
  • Variables and constraints — table of every JuMP variable and constraint family with row counts. Use the Show filter to restrict to variables or constraints, and the Search field to find a family by name.
    • 
        


        
Technology dependencies tab

        
Macro-level system flow diagram: which technologies feed which activities, and which activities feed which technologies.

        
    
          
  • Diagram detail — Sector / category groups aggregates technologies into bundles for a system-level view, while Individual technologies shows every technology as its own node (use sparingly — the graph gets dense fast).
    • 
          
  • Max activities — caps the number of activities included in the diagram, ranked by importance, so the graph stays readable.
    • 
          
  • Sectors / Subsectors / Technology categories filters — restrict the diagram to a subset; uncheck what you do not need.
    • 
          
  • Refresh graph — re-renders the diagram with the current filters.
    • 
          
  • Activity rows — companion table listing each activity along with its producers, consumers, and edge counts.

MGA workspace

        
Model-Generated Alternatives (MGA) explore near-optimal system designs — configurations whose total system cost stays within a user-chosen slack of the least-cost optimum, but whose technology mix differs. Useful when the least-cost objective alone cannot capture every political, environmental, siting, or implementation concern. The implementation is solver-backed: every alternative is a real LP over the original IESA-Opt constraints plus a system-cost cap, and ORACLE-style closest-point refinements target the largest unexplored gap in a reduced design space (see the MGA documentation for the formulation).


        
Configure tab

        
Defines the campaign and previews the seed directions before any solve runs.

        
    
          
  • Workbook + temporal mode + periods + representative days + extreme periods — same controls as the Single Run setup; they pin the underlying IESA-Opt model that every alternative will solve.
    • 
          
  • Solver and Solve method — chooses the LP backend used for the baseline and every alternative. Gurobi barrier_crossover is the default when a license is available; HiGHS barrier is the cross-platform fallback.
    • 
          
  • Cost slack (%) — how far above the least-cost optimum the alternatives are allowed to go (typically 1–10%). Larger slack means more design freedom and more diverse alternatives.
    • 
          
  • Directions — total number of alternatives to solve. Split automatically between VMM seed directions, low-discrepancy parallel seeds, and ORACLE refinement directions.
    • 
          
  • ORACLE iterations and ORACLE batch — control how aggressively the closest-point LPs refine the largest unexplored gap.
    • 
          
  • Tolerance — target estimated max-error (in normalized design units) at which ORACLE refinement stops.
    • 
          
  • Workers — reserved for future parallel solves; currently the campaign runs alternatives sequentially with the full thread budget per solve.
    • 
          
  • Preview design — lists the planned directions with phase labels (vmm, parallel-seed, oracle-refine), dominant group, and weight summary, without solving anything.
    • 
          
  • Run MGA campaign — submits the campaign and switches to the Progress tab automatically.
    • 
        


        
Progress tab

        
Live status for the campaign that is currently solving (or the last one started).

        
    
          
  • Status pill + headline — campaign name, state, and current stage message (baseline, seed, ORACLE iteration, finalize).
    • 
          
  • Progress bar — alternatives completed vs. planned, with current-iteration ORACLE max-error trace alongside.
    • 
          
  • Stage strip — six-step pipeline (prepare → baseline → seed solves → ORACLE → finalize → complete).
    • 
          
  • Workers card — configured worker count, threads-per-solve, solver, solve method, and the direction currently being solved (label, phase, started-at).
    • 
          
  • Directions table — every planned direction with status (queued / running / solved / failed), elapsed time, and any solver error message. Rows update in place as the campaign progresses.
    • 
          
  • Run log — condensed campaign trace including baseline cost, cost cap, ORACLE iteration before/after errors, and accepted candidate counts.
    • 
        


        
Results tab

        
Shows the finished campaign. The left sidebar lists every MGA campaign captured by the server (newest first); click one to load its alternatives. The main panel has two stacked sections.

        
MGA results — the campaign-level certificate and per-alternative diagnostics:

        
    
          
  • Certificate cards — baseline cost, cost cap, slack used, exploratory dimensions, initial vs. final estimated max error, ORACLE iterations, and convergence flag.
    • 
          
  • ORACLE convergence chart — max-error trace across iterations (before vs. after).
    • 
          
  • Slack-vs-diversity scatter — one marker per alternative; X-axis is the system-cost slack actually used (%), Y-axis is the design-space diversity score, color is the worker. Hover for direction label, dominant group, and worker.
    • 
          
  • Alternatives table — one row per direction with phase, status, dominant group, system cost, cost index, slack used, diversity, max-error contribution, and solver.
    • 
        

        
Investments across alternatives — turns the per-alternative optimal investment decisions into actionable insight. Every solved alternative reports its full per-technology installed stock and new investment; the panel aggregates those across the campaign:

        
    
          
  • Summary line — total number of technologies invested in, how many were built in every alternative, and how many were optional.
    • 
          
  • Sort by selector — reorders the envelope chart by Highest capacity, Largest range (absolute spread), Largest relative spread, or Baseline level.
    • 
          
  • Investment envelope chart — horizontal bar showing the min→max range each technology takes across all alternatives. The bar is color-coded by category (green = low-regret, orange = high-volatility, indigo = optional, blue = stable). A black diamond marks the baseline (least-cost) level so you can see at a glance whether MGA pushes the technology up, down, or both.
    • 
          
  • Low-regret investments — top techs that are built in every alternative with a tight relative spread (≤5%). These are the robust "no matter which near-optimal future you pick, you build this" capacities.
    • 
          
  • High-volatility investments — top techs whose installed level varies the most across alternatives (relative spread ≥40%). These are the levers MGA finds — technologies the model can swap in or out without breaking the cost cap.
    • 
        

        
Use the categories together: low-regret tells you what every near-optimal pathway agrees on; high-volatility tells you where there is genuine flexibility (and therefore where political, social, or implementation preferences can decide between alternatives without paying a meaningful cost penalty).
